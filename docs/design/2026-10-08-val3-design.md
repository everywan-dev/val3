# VAL3 design

Status: agreed 2026-10-08 (design interview with the project owner). Decision records: ADR 0001, ADR 0002 (index delivery).

## 1. Goal

Every session that establishes something worth knowing leaves it behind as **verified facts**
and **recipes**: what was asked, the correct path, the result, and how to reproduce it. The next
session, on any machine and in any project that shares the vault, receives that knowledge without
re-investigating. Knowledge that can be derived from a live source (code structure, database
schema) is not stored: VAL3 registers the external tools that answer it and points the agent to
them.

Two guarantees, both given by the harness and never by the model remembering an instruction:

- **Capture:** every closed or compacted session is queued for extraction; a session whose
  extraction did not run is processed at the next session start.
- **Delivery:** the index of recipes, tools and preferences is loaded at every session start, and
  every prompt is matched against the vault before the model answers.

What is not guaranteed: that the extractor picks everything relevant, or that an admitted fact is
still true. Admitted facts are trusted (no re-verification on recall); a selective audit is
deferred work (section 12).

## 2. Non-goals

- Storing session transcripts, failed attempts or live project state (pending work stays in the
  project's own `TODO.md`/`SESSION.md`).
- Storing derivable knowledge (code graphs, schemas): external tools own it.
- Periodic freshness probes, verdicts or drift detection (retired from validated-memory 2.x).
- Filtering sensitive data in cited evidence (deferred).

## 3. Vocabulary

See `CONTEXT.md`. In short: a **vault** holds **entries** of kind **fact**, **recipe**,
**preference**, **decision** or **tool**; the **inbox** is the harness's native auto-memory
directory; the **writer** is the only code path that changes a vault; the **review list** holds
what needs a human decision.

## 4. Architecture

```
 session (Claude Code)
   │ model writes notes ──────────────► inbox (native auto-memory dir, local)
   │ transcript JSONL ────────────────┐
   │                                  │
 hooks: PreCompact / SessionEnd ──► pending queue (local file, fast, < 1.5 s)
        SessionStart ─────────────► drain pending queue (catch-up)
                                      │
                                      ▼
                      extractor (detached `claude -p`, fixed prompt)
                      reads changed inbox notes + transcript
                      emits candidates with literal evidence quotes
                                      │
                                      ▼
                      writer (one module, one transaction per candidate)
                      checks quote exists in transcript ── no ──► discard
                      fact + evidence ───────────────────────────► admitted
                      recipe / user confirmation / supersession ─► review list
                                      │
                                      ▼
                      PostgreSQL: database `val3`, one schema per vault
                                      │
 delivery:                            ▼
   SessionStart ─► index of recipes, tools, preferences as hook context (≤ 10 000 chars)
   UserPromptSubmit ─► full-text match on prompt ─► inject ≤ 10 000 chars
```

## 5. Capture

### 5.1 Inbox

The native auto-memory directory (`~/.claude/projects/<project>/memory/`) is left where the
harness puts it and used as the inbox. The model writes notes there as it normally does. Each note
the harness writes carries `originSessionId` in its frontmatter, which names the transcript that
holds its evidence.

- VAL3 tracks each note by content hash; any change, by the model or by anything else, makes the
  note a candidate again.
- After processing, VAL3 appends to the note one line with the entries it became
  (`Recorded in VAL3 as <vault>#<id> (verified)…`), keeping the body; a later line merges into it.
  *(2026-11-07: replacing the body lost the parts of a multi-item note that no entry held; the
  harness injects only `MEMORY.md`, so a shorter body saved no context.)*
- Adopting projects set `autoDreamEnabled: false`. The hash tracking covers the case where a
  harness-side consolidation rewrites notes anyway; VAL3 does not write while
  `.consolidate-lock` exists.

### 5.2 Pending queue

`PreCompact` and `SessionEnd` append `{session_id, transcript_path, cwd, event, ts}` to a local
queue file and spawn the extractor detached. They do nothing else: `SessionEnd` has a 1.5 s
budget. `SessionStart` drains entries whose extraction did not complete. An entry is removed only
after the writer committed its candidates.

Transcripts are deleted by the harness after 30 days, so evidence quotes are copied into the
vault, never referenced.

### 5.3 Extractor

A detached `claude -p` run with a fixed, versioned prompt. Input: the changed inbox notes of the
session and its transcript. Output: JSON candidates, each with kind, statement, reproduction
(query, command or tool call), literal evidence quote, index names and search keywords in both
English and Spanish. The extractor discards trial and error: only the final correct path counts.

The agent may also save during the session with `val3 save`, which produces a candidate that goes
through the same writer.

## 6. Admission (the writer)

One module performs every vault change, in one transaction per candidate. Concurrency between
machines and sessions is handled by PostgreSQL (transactions and constraints), not by a central
service.

| Candidate | Rule |
|---|---|
| Fact with evidence quote (command/query/API output, passing test) | Quote must appear literally in the transcript; then admitted. Not re-executed. |
| Imported candidate (`val3 import`) | Quotes checked with `git show` at a commit the importer fixes; every candidate goes to the review list (ADR 0003). |
| Fact validated only by user confirmation | Review list. |
| Recipe | Review list. |
| Fact contradicting an admitted fact | New fact admitted as superseding; old one kept and linked; recipes citing the old one flagged; supersession shown in the review list. |
| No literal quote found | Discarded (logged). |

## 7. Store

- PostgreSQL on a reachable server; database `val3`; **one schema per vault**.
- A project declares its vaults in a versioned file at its root (`val3.toml`): its **home** vault
  (written) and **linked** vaults (read-only). Several projects may share a home vault.
- Connection by `pg_service.conf` service name; password in `.pgpass` or a secret manager;
  nothing secret in the project file.
- Roles: per project or machine; write on home vaults, read on linked vaults.
- Specialized vaults, vault notes, ad hoc reads and mirrors of other hosts' vaults:
  `docs/design/2026-11-07-vault-sharing-design.md`.
- Append-only: rows are never updated or deleted; supersession is a new row plus a link. Every
  write appends to an event log (what, project, session, machine, time).
- Backup: `val3 backup` (`pg_dump` of the whole database: every vault, `val3_common`, extensions,
  privileges); restore with `pg_restore` into a new database (operations design, 4.3).
- Server unreachable: hooks fail open (one warning per session); inbox notes and queue entries
  wait locally.

### 7.1 Data model (sketch; the plan fixes columns and constraints)

| Table | Holds |
|---|---|
| `entry` | id, kind, title, statement, created_at, origin project/session/machine, `superseded_by` |
| `knowledge_index` | named indexes per vault (e.g. flows, modules) |
| `entry_index` | entry ↔ index, many-to-many |
| `evidence` | entry, kind (query/command/api/test/user/file), reproduction, literal quote, session, ts |
| `recipe_parameter` | recipe, name, description |
| `recipe_step` | recipe, order, action, optional tool entry |
| `step_fact` | step ↔ fact |
| `recipe_example` | recipe, parameter values, result, session |
| `review_item` | candidate payload, reason, status (pending/approved/rejected), decided_by, ts |
| `event` | append-only log |

A recipe is a row whose parameters, steps, cited facts, evidence and worked examples come from
these relations: "trace an invoice" resolves to `vault#id` and from there to everything needed to
reproduce it. Parameters are declared explicitly, never inferred from examples.

References: `<vault>#<id>`.

## 8. Delivery

- **Session start:** the `SessionStart` hook injects an index grouped by knowledge index
  (recipes, registered tools, preferences) as hook context, within the harness limit of 10 000
  characters. The harness reads `MEMORY.md` before `SessionStart` hooks run, so VAL3 leaves
  `MEMORY.md` to the harness (ADR 0002). No model decision involved.
- **Every prompt:** a `UserPromptSubmit` hook runs PostgreSQL full-text search (English and
  Spanish configurations, accent-insensitive) over entries and tools of the home and linked
  vaults, and injects the best matches with their source vault, within 10 000 characters. A
  matching recipe is injected with its step list and fact references; the agent reads the rest
  with `val3 recall` / `val3 show`.
- Matching: stop words (the stock English and Spanish lists plus a short list of their own) do
  not count. In a vault of 10 or more live entries, a word most entries hold weighs 0 (the
  project's own vocabulary), a word a single entry holds weighs 2, any other 1; an entry matches
  when its shared words weigh 2, or all the query weighs. Typed prompts get up to eight entries;
  harness turns (`source` other than `user` or `sdk`: peer messages, task notifications, wakeups)
  get three, since their long model text shares a couple of words with almost any entry.
- Semantic search (`pgvector`, local embedding service): `docs/design/2026-10-09-semantic-search-design.md`.

## 9. External tools

`val3 tool add` registers a tool (skill, MCP server, CLI) as an entry of kind `tool`: name, type,
description, the questions it answers, environment (where it runs; repository URL to clone),
priority. Tools are part of the `MEMORY.md` index and of per-prompt matching. For derivable
knowledge, a registered tool takes precedence over any stored fact.

## 10. Review list

`val3 review` lists pending items; `val3 review --tty` walks them in the terminal with a card per
item (for a supersession, the old and the new entry) and approve/reject/skip/quit; each decision
goes through the writer. A reproduction is shown, never run. A local web page is deferred (section
12). Detail: `docs/design/2026-10-11-operations-design.md`.

## 11. Scope and migration

- Claude Code is the full agent (capture and delivery). Other agents use `val3 recall` only.
- `val3 import` (plan 3b) reads a validated-memory 2.x adopter at one pinned commit, checks each
  quote against the repository files at a commit it fixes, and puts every candidate on the review
  list (`docs/design/2026-10-12-import-design.md`, ADR 0003).
- Runtime: Python standard library plus one PostgreSQL driver.

## 12. Deferred work

- Selective audit of admitted facts reporting a truth percentage.
- Sensitive-data filtering of evidence quotes.
- Rules for asking a vault owner to correct a fact found wrong by another project.
- A local web page for the review list (bound to 127.0.0.1, token in the URL).
